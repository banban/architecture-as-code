# TOGAF 10 — Architecture Development Method (ADM)

> **Purpose:** Authoritative reference for the ADM phases, their inputs, key activities, and outputs. Use this file to ensure every architecture project follows the correct process steps and produces the right artefacts.

---

## Overview

The **Architecture Development Method (ADM)** is the core of the TOGAF framework — a multi-phase, iterative approach to develop and use Enterprise Architecture to shape and govern business transformation and implementation projects.

The ADM is a tested and repeatable process that addresses business needs through:
1. **Visioning** — clarifying what the architecture must achieve
2. **Architecture Definition** — designing the future state across all four domains
3. **Transformation Planning** — identifying how to get there
4. **Architecture Governance** — ensuring implementations comply

### Requirements Management (Central Hub)
Runs continuously across all phases. Manages the Architecture Requirements Repository (strategic, segment, and capability requirements). In Agile implementations, requests are generated by a concern backlog.

## Preliminary Phase — Framework and Principles

**Purpose:** Prepare the organisation for successful TOGAF adoption. Establish the architecture capability, customise the framework, and define governing principles.

### Key Activities
- Develop Architecture Principles, define security principles and non-architectural inputs
- Select reference models, viewpoints, and tools
- Customise and tailor TOGAF to the organisation
- Conduct stakeholder analysis and map the stakeholder landscape
- Perform Capability Assessment; establish resource planning for architecture work
- Define Architecture Continuum and customise the TOGAF framework
- Document Architecture Principles Catalog (APC)
- Accomplish engagement policy; establish the security context (Security Resources Plan, Risk Appetite and Tolerance)

### Key Outputs
- Architecture Principles Catalog (APC)
- Request for Architecture Work (RAW)
- Security Blueprint
- Architecture Vision Document
- Tailored Architecture Framework
- Organisation/Actor Catalog, Role Catalog

## Phase A — Architecture Vision

**Purpose:** Develop a high-level aspirational vision of the capabilities and business value to be delivered as a result of the proposed Enterprise Architecture.

### Key Activities
- Establish an architecture project; define "SMART" objectives (Specific, Measurable, Actionable, Realistic, Time-bound)
- Identify stakeholders, concerns, and business requirements; value capabilities
- Elaborate business goals; define scope; develop Solution Concept Diagrams
- Convert concerns to needs and requirements; develop an overview of existing pain points
- Business Transformation Readiness Assessment
- Develop Architecture Vision; define multiple managed states (candidate, current, transition, target)
- Secure approvals; define architecture requirements repository (ARR)

### Key Outputs
- Statement of Architecture Work (SAW)
- Communications Plan (CP)
- Architecture Vision (summary of changes and architecture definition)
- Architecture Requirements Specification (ARS) — initial
- Risk Catalog, Stakeholder Catalog, Business Scenario

## Phase B — Business Architecture

**Purpose:** Develop the Target Business Architecture, describing how the enterprise needs to operate to achieve business goals.

### Key Activities
- **Strategy Domain:** Business Model, Principles, Goals, Drivers, Constraints, Exceptions, Innovations, Business Vision and Mission
- **Structural Domain:** Organisation Map, Organisational Standards, Business Processes/Functions, Business Services and Products; Business Model Canvas (current state)
- **Logical Design Opportunities:** Business Footprint Diagram, Business Risk Model, Business Model Canvas (future state)
- Business Process Modelling; Partitioning model reflecting operational model of each org unit
- Capability/Value Stream Matrix, Strategy/Capability Matrix, Capability/Organisation Matrix; Security Policy Architecture
- **Operational Domain:** Operational/Capability Model, Lifecycle (reuse/retire)
- Achieving Business Agility Assessment
- Assess Business Capabilities Catalog (G233e, G206e)

### Key Outputs
- Business Architecture Blueprints
- Business Architecture Statement of Work
- Value Stream/Capability Matrix
- Business Risk Model
- Business Capabilities Catalog
- Organisation Map

---

## Phase C — Information Systems Architecture

**Purpose:** Develop the Target Information Systems Architectures (Data and Application) supporting the Target Business Architecture.

### Key Artefacts — Data Architecture
- Data Entity/Data Component Catalog
- Data Security Diagram
- Process/Application Realisation Diagram
- Software Engineering Diagram; Software Distribution Diagram
- Data Dissemination Diagram; Data Lifecycle Diagram
- Application/Data Migration Diagram

### Key Artefacts — Application Architecture
- Logical, Conceptual, and Behaviour Diagrams
- Application Architecture Models
- Security Classification
- Role/Application Matrix; Application/Function Matrix; Application Interaction Matrix
- Application Use-Case Diagram
- Application/Organisation Matrix
- API to Consumer (Interaction) Mapping
- Atomic Business Functions (ABF) to Microservices Mapping
- Interface Catalog; Application Portfolio Catalog; Security Services Catalog
- Communication Diagram

### Key Activities
- Define data and application principles
- Identify required improvements in customer experience (Solution Continuum)
- Validate Architecture Building Blocks (ABBs); analyse gaps
- Identify candidate Architecture Roadmap components

---

## Phase D — Technology Architecture

**Purpose:** Develop the Target Technology Architecture supporting the Target Information Systems Architectures.

### Key Artefacts
- Technology Standards Catalog
- Technology Architecture Models
- Technology Portfolio Catalog
- System Management Checklist; Security Checklist
- Decomposition Diagram; Environments and Locations Diagram
- Platform Processing Diagram
- Networked Computing/Hardware Diagram
- Network and Communications Diagram
- Application/Technology Matrix

### Key Activities
- Address technological limitations; identify logical and physical technology components
- ABB Technology & Security Assessment; Procurement activities (COTS, RFI, RFP)
- Refine Statement of Architecture Work (SAW); draft ADD and ARS
- Services Deployment Plan; SLO/SLA; Control/Security Objectives
- SABSA Business Attribute Profile (concept of balancing risks)

---

## Phase E — Opportunities and Solutions

**Purpose:** Generate the initial complete version of the Architecture Roadmap, based on gap analysis and capability assessments.

### Key Activities
- Governance Checkpoints; Success/Failure Criteria; Acceptance Procedure; Conformance Requirements
- Determine and confirm key corporate change attributes
- Determine business constraints for implementation; Solutions and Dependencies Matrix
- Consolidated Gaps; Choosing a Method using the Cynefin Framework:
  - **Complex** → SCRUM
  - **Complicated** → Kanban/SCRUM
  - **Obvious** → Waterfall
  - **Chaotic** → Agile
- Capability Architecture; Digital Enablement; Digital Domain; reconcile interoperability requirements
- Digital Enterprise Readiness Assessment; identify Transition Architectures (releases)
- Determine whether an incremental approach is required
- Implementation Factor Assessment and Deduction Matrix; Physical Resources Allocation Assessment
- Confirm readiness and risk for business transformation; Migration Readiness Assessment
- Roadmap of Work Packages (WP), MOE, and CSFs; Risk Treatment/Mitigation Plan
- Define overall SBBs based on ABBs; Benefits Diagram; Project Context Diagram

### Key Outputs
- Architecture Roadmap (initial)
- Solution Building Blocks (SBBs)
- Transition Architecture definitions

---

## Phase F — Migration Planning

**Purpose:** Finalise a detailed Implementation and Migration Plan in coordination with the portfolio and project management framework.

### Key Activities
- Strategic Requirements; Regression Planning; assign a business value to each Work Package
- Group Work Packages into portfolio; transforming WPs to project initiation
- Handover WPs to PMO as projects; confirm Architecture Roadmap; update ADD
- Project and Portfolio Breakdown of the implementation; Migration Roadmap
- Migration Checklist; Security Impact Analysis
- Architecture Contract; Business User Contract
- Architecture Alternatives and Trade-Offs; Implementation and Migration Plan (I&MP)
- Project Charters; Breakdown of implementation

### Key Outputs
- Implementation and Migration Plan (I&MP)
- Architecture Contract (signed)
- Project Charters
- Updated Architecture Roadmap

---

## Phase G — Implementation Governance

**Purpose:** Provide architectural oversight of the implementation, ensuring conformance with the Target Architecture.

### Key Activities
- Identify who is responsible, involved, and accountable (RACI)
- Architecture Governance Framework; Implementation Governance Model
- Governance Organise Structure; Segment Architecture
- All changes within the scope of Target Architecture; Development of Target Architecture
- Risk/Compliance Assessment against SLAs/OLAs, standards, regulatory requirements
  - Conformance levels: Irrelevant → Consistent → Compliant → Conformant → Fully Conformant → Non-conformant
- Architecture Board responsibilities: Accountability, Responsibility, Transparency, Fairness
- Post-implementation review to close implementation; capture reusable ABBs and SBBs
- Architecture Compliance Reviews; Governance and Approval Plan
- Potential Governance Tiers: Corporate, EA, Business, Domain, Implementation

### Key Outputs
- Opportunities Catalog
- Architecture Compliance Reviews
- Governance and Approval Plan
- Implementation Governance Model

---

## Phase H — Architecture Change Management

**Purpose:** Ensure that changes to the architecture are managed in a controlled way, maintaining the architecture's relevance and integrity.

### Triggers for Change
- Request from Sponsor via EA team
- Request from business sponsor stakeholder (top-down)
- Request by Data Architect discovery opportunity (bottom-up)
- Request from market/contractor/partner
- Request due to environment change
- Request from Governance
- Request to solve implementation/performance issues

### Key Activities
- Change Rationale; Anticipated Impacts; Drivers for Change; establish a value realisation process
- Architecture Vision, Architecture Domains, Enterprise Strategic Architecture
- Deploy the process and tools to measure business value
- Enterprise Continuum; provide analysis for architecture change management
- Develop change requirements to meet performance targets
- Change & Rollback Plan; operational performance monitored against target requirements
- Architecture Change Request; Update Architecture Requirements; Activate the process to implement change

### Key Outputs
- Architecture Change Request
- Updated Architecture Requirements
- Recommendations on management of requirements

## ADM Iteration Types

| Iteration | Phases Involved | Purpose |
|---|---|---|
| Architecture Capability Iteration | Prem–A, Prem–H | Establish or improve the EA capability itself |
| Architecture Development Iteration | B–C–D–E–F | Develop architectures across domains |
| Transition Planning Iteration | E–F | Plan and sequence implementation |
| Architecture Governance Iteration | G–H | Govern implementation and manage change |

### Change Management Flow
- **H → G:** Re-architecture, large incremental change
- **G → H:** Disciplinary Process, Dispensation, Exemption
- **Simplification Change:** Small incremental change

## ADM and Agile / SCRUM Compatibility

The ADM is compatible with Agile and SCRUM iterations:

- Each ADM phase maps to one or more sprint cycles
- **Minimum Viable Architecture (MVA):** Each sprint delivers the minimum architecture that is realisable and adds business value
- **No-regret decisions:** Decisions that work well in all scenarios are preferred early
- Agile systems keep architecture simple; only add complexity when needed
- Working software is the primary measure of progress (Agile principle)
- Management 3.0 delegation levels apply: Tell → Sell → Consult → Agree → Advise → Inquire → Delegate
